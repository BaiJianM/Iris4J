# 查询语义缓存接入多路召回——问题点与风险点规划

> 状态：**规划稿，未实施**（2026-09-13）。老板拍板后才动代码。
> 前置阅读：总览 §5.5（RAG 混合检索第一轮）、`SemanticCachedEntityQueryService` 源注释。

## 1. 背景与目标

RAG 第一轮已给 **LLM 响应缓存**落地三通道召回（稠密 + BM25 词法 + 多查询改写）→ RRF → rerank 精判。本规划回答：**实体查询语义缓存（`SemanticCachedEntityQueryService`）要不要、以及如何接入同一套多路召回**。

## 2. 现状盘点（读码实据）

| 维度 | 现状 | 出处 |
|---|---|---|
| 装饰链 | AccessControlled → semantic → exact → Default | 各类 `@Qualifier` 注入 |
| 候选域 | hardKey 精确等值收窄（entity/tenant/fields/分页/非 STRING 过滤值/字符串过滤键集合），**只有 STRING 过滤值**参与模糊 | `RequestCanonicalizer.canonical` + `splitFilters` |
| 值级门 | 纯余弦 ≥ 阈值（yml 0.88 标定值；代码缺省 0.85），无槽位校验、无 rerank | `SemanticCachedEntityQueryService.query` |
| 候选查找 | `cacheService.getAllMatching(pattern)` = SCAN `…:sem:{fp}:{hardKey}:*` | 同上 |
| 授权隔离 | 行级 tag 注入发生在语义缓存**之前** → tags 不同 → hardKey 不同 → 天然隔离；字段裁剪在缓存返回之后（存完整行） | `AccessControlledEntityQueryService` |
| 失效 | TTL 60s + CDC 主动失效（按实体前缀删）+ 指纹段隔离（换模型走 SemanticReindexService 迁移） | CacheService / SemanticCacheEviction |
| 时效旁路 | `QueryRequest.fresh` 已穿透本层跳过读（2026-09-13 落地） | `request.fresh()` 早退分支 |

## 3. 核心立场：这是「精度增强」，不是「召回扩展」

LLM 缓存与实体查询缓存的**成本结构完全相反**，决定了接入方式必须不同：

| | LLM 响应缓存 | 实体查询语义缓存 |
|---|---|---|
| miss 成本 | **高**：一次真实 LLM 调用（秒级 + 烧 token） | **低**：一次 Query Engine 查询（10~100ms） |
| 错答成本 | 高（错误答案被缓存复用） | **∞**（结构化数据错答直接摧毁信任） |
| 结论 | 召回扩展：宁滥勿缺，多通道捞回候选 | **精度增强**：多通道做「双通道一致性」，而不是扩大模糊面 |

由此推出三条设计红线：

1. **不做 LLM 多查询改写**。改写结构化查询的过滤值 = 捏造数据（把 `city=上海` 改写成 `city=上海市` 去查，是造了一个没见过的请求），且 miss 常态化下每次都白付秒级 LLM 延迟。多查询通道在缓存路径永远不开。
2. **词法通道只作「一致性证据」，不扩大候选面**。BM25 对短 STRING 值（城市名/状态名）无分辨力——「上海」与「上海市」的 bigram 词项是包含关系，词法上必然「相似」。它的正确用途是：**候选必须同时过余弦门与词法证据两道门才放行**（必要条件），而不是把词法命中也并进候选池。
3. **rerank 精判默认不上**（见 §4 经济学）。

## 4. 问题点清单

### P-1 命中经济学可能是负收益（Phase 0 决策门，先实测再动工）

命中一次语义缓存的净收益 = `省下的 Query Engine 时间 − (embed 查询 ~42ms 远程 + SCAN 候选 + N 次余弦 + JSON 反序列化)`。
若目标查询本身只要 10~50ms，**当前实现的命中路径可能比直接查库还慢**。再加 rerank：每次未命中都白付 N+1 次远程精判往返（150~300ms+），而 miss 是常态——等于给所有未命中请求加延迟惩罚。

**Phase 0（只读实测，改代码前必做）**：用 ecomm 真实查询统计「Query Engine 耗时分布」与「命中路径各段耗时」，得出收益临界线。若收益为负，结论就是「保持现状，不接入」——这也是一个合法的拍板结果。

### P-2 候选查找是请求路径 SCAN（红线三踩 T25/T28/T31 同类）

`getAllMatching` 的 SCAN 虽被 hardKey 收窄（基数 = 同 hardKey 的语义条目数，通常个位数），但模式与「按前缀枚举禁 SCAN」的既有红线同构。若接入多路召回扩大候选面，SCAN 基数随之上涨。**无论如何应先索引化**：语义条目挂 `iris:{ns}:cacheidx:sem:{entity}:{fp}:{hardKey}`（SET），候选查找改 O(1) SMEMBERS，与实体缓存/LLM 缓存既有索引方案对齐。

### P-3 值级门的「等价 vs 包含」边界不会被多路召回改善

余弦 0.88 是按「同义 0.92 / 同类不同值 0.53 / 无关 0.31」标定的；「上海 ≠ 上海市浦东新区」这类**包含但不等价**的负对，词法通道没有分辨力（词项包含），rerank 分数有方向性（双向 min）可试但未标定。**该边界的最终防线仍是阈值 + 金标回归，多路召回不解决它**。误把希望寄托在新通道上 = 引入新风险而不解决旧风险。

### P-4 澄清流规范化条目（遗留④）语义在实体查询侧不存在

LLM 缓存有「澄清答复规范化回写」，实体查询缓存没有对应物、也不需要（查询请求本身是结构化的，无指代问题）。规划上明确**不复刻**该机制，避免画蛇添足；但遗留④的复测（澄清流复测）与本规划无耦合，可独立进行。

### P-5 fresh 语义必须保持穿透

若后续重构本层（索引化/多通道），`request.fresh()` 的跳过读语义必须原样保留（2026-09-13 刚落地并有冒烟）。回归项加入验收清单。

## 5. 风险点清单

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | 错答成本∞：任何扩大模糊面的改动都在放大错答概率 | 高 | 双通道一致门只收紧不放宽；空结果不回写语义既有规则保留 |
| R2 | rerank 给所有 miss 加 150~300ms 固定延迟 | 高 | 默认不上；若上，仅对「余弦灰区」候选启用（门内窄带才精判） |
| R3 | SCAN 基数随候选面扩大上涨 | 中 | 先索引化（P-2），再谈通道 |
| R4 | BM25 词法对短值无分辨力，「词法命中」被误当「语义证据」正用 | 中 | 词法仅作必要条件（一致性门），文档与代码注释双写明 |
| R5 | 换 Embedder 后旧语义条目污染（指纹隔离已有，但索引化后索引 key 必须含指纹段） | 中 | 索引 key 带指纹段，沿用 SemanticReindexService 迁移路径 |
| R6 | 容量淘汰（SemanticCacheEviction 抽样 SCAN+淘汰）与索引化的写路径不一致 → 索引悬挂成员 | 低 | 索引不设 TTL、悬空成员惰性 SREM（对齐 LLM 缓存 memidx 既有方案） |

## 6. 分阶段路线（供拍板）

- **Phase 0（只读实测，半天）**：hit 路径 vs 直查路径耗时对比，产出收益临界线 → **决策门：收益为负则到此为止**。
- **Phase 1（索引化，1 天）**：语义条目候选查找去 SCAN（P-2/R3/R5/R6 一次解决）。与多路召回无关、独立有收益（红线合规），**无论后续走不走都建议做**。
- **Phase 2（精度增强，可选）**：词法一致性门（必要条件，不扩面）+ 金标回归（复用 `scripts/calibrate-qwen3-thresholds.py` 的 VALUE_POS/NEG 对，补「上海/上海市浦东新区」类包含负对）。rerank 灰区精判默认不做，除非 Phase 0 显示命中收益足够大、值得为它付 miss 延迟。
