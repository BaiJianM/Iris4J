# Agent 复杂查询多轮不出结果：瓶颈分析与改进方案

> 2026-09-11。背景：演示页 Agent 在 MCP 工具辅助下回答数据问题时，需求稍复杂（多表、大跨度关联、统计类）就陷入
> 长思考 + 多轮工具调用，最终仍无法给出结果。本文基于**代码实证**（非推测）定位根因，给出方案与落地优先级。
> 结论先行：**能力缺口是主因（缺聚合原语），上下文过载是放大器，护栏缺位把失败变成死循环。**

---

## 0. 结论（TL;DR）

1. **主因是工具面缺 3 个原语**：聚合（GROUPBY/COUNT）、IN 过滤、结果裁剪。统计/TopN/分布/维表翻译/跨表取数这些
   高频场景在当前工具面**无解**，模型只能穷举分页（每页 ≤200 行）或逐 key 过滤 —— 5 万行 = 250 页，3000 渠道 = 3000 次调用。
2. **上下文过载是放大器**：schema 摘要把 135 表 / 686 字段全量注入每轮 system prompt（实测 **14,432 字符 ≈ 8k–11k token**）；
   工具结果 200 行全字段 JSON **无截断**直接回灌；历史再注入最多 7.2k 字符。推理空间被挤干后模型进入复读，最终
   `finish_reason=length` 报错收场。
3. **护栏缺位把「答不出」变成「死循环 + 误导性报错」**：reasoning 无循环检测；输出预算默认 4096 对推理模型偏小；
   截断异常被包装成「工具执行链路异常」，0 次工具调用也报「模型仍在请求工具」。
4. **不建议做「运行时由 AI 动态生成 MCP 工具」**（§4 专项研判）。缺的是少量正交原语，不是更多工具；
   AI 的正确位置是**离线研判**（决定补哪些原语）与**运行时生成查询参数**（它本来就在做）。

**落地优先级**：P0 改提示词 + 元数据 + 循环护栏（当天，纯字符串/小护栏）；P1 结果裁剪 + Schema 分级注入（1–2 天）；
P2 聚合原语 `aggregate_entity`（2–4 天，治本）；P3 预关联展开 / IN 查询 / 受控只读查询（按需）。
**自进化循环**（§7）：信号采集与失败案例库可随 P0/P1 一起落，工作台与范例检索在 P2 之后 —— 它消费前者的产物。

## 1. 现象与实证样本

2026-09-10 晚的失败案例（演示页实测，qwen3.7-flash→qwen3.8-max 均可复现）：

- 问题：「每种支付渠道各有多少笔支付，哪个最多」。
- 模型先取 5 页 × 200 行 = **1000 行全字段 JSON** 进上下文，然后在自己的思考流里逐个枚举 channel_id 并人肉计数；
- 发现总行数 50,000、渠道 3000 个后，正确地判断「逐页穷举 250 页不可行」，并找到了唯一可行的替代方案
  （按 `filters:{channel_id:N}` 逐渠道查 `total`）；
- 但随后思考流进入复读（同一句话重复上百次），从未真正发出工具调用，最终烧光 4096 输出预算 →
  `finish_reason=length` → 报错终止。**0 个工具调用、0 个答案。**

这个样本集中暴露了全部四类问题：能力缺口、上下文爆炸、推理失控、护栏误导。

## 2. 根因分析（按影响排序）

### R1（根本）工具面没有「聚合」原语 —— 统计类问题在原语层面无解

`EntityToolFactory` 生成的查询工具参数面只有
`fields / filters / rangeFilters / textFilters / page / pageSize / sortField / sortDesc / tenant`
（`api/.../mcp/EntityToolFactory.java:201-274`），**没有 groupBy、没有 count/sum/avg、没有 distinct**。

后果：「每个渠道多少笔」这类 OLAP 语义的问题，唯一路径是把明细拉到模型上下文里**人肉聚合**：
- 50,000 行 ÷ 200 行/页 = 250 次调用（`PageRequest.MAX_PAGE_SIZE=200` 是防打爆 Redis 的硬上限，**不该放松**）；
- 或 3000 渠道 × 1 次等值过滤调用。
两条路都是轮数炸弹，且每次调用的结果还要原样回灌上下文（见 R3）。

**这不是模型笨，是工具面表达不了这个问题。** 再强的模型也只能选「穷举」或「放弃」，而系统提示词
（规则 1「涉及数据的问题必须调用工具获取真实结果」）把「放弃」也堵死了。

### R2（根本）没有 join 语义，跨表靠模型脑内嵌套循环

schema 里的 `relatedEntity` 元数据只回答「外键指向哪张表」，不回答「怎么合」。
系统提示词规则 3 的跨表范式是：查源表拿主键 → `get_related_entities` 导航。一次 3 表关联 = 3~6 轮工具调用，
每轮回灌一页 200 行；跨表聚合（如「按渠道名称统计」）还需要模型先拉全维表、在上下文里维护 id→名称映射。

### R3（放大器）工具结果无裁剪，整页 JSON 原样回灌

`AgentToolDispatcher` 与 MCP 的 `call_entity_tool` 返回结果**没有任何行数/字节截断**
（全文件 grep `truncat|MAX_.*RESULT|limit` 零命中）。200 行 × 全字段直接进 `tool_result`。
工具参数里的 `fields`（「要返回的字段列表，为空返回全部字段」）**存在但没人告诉模型用** ——
失败样本里模型要的只是 `channel_id` 一列，却拿了 9 列 × 200 行。

### R4（放大器）Schema 摘要全量常驻注入

`DefaultAgentService.schemaDigest()` 把 namespace 下**全部实体、全部字段**拼进 system prompt
（`fields → relatedEntity` 全保留，无截断、无按需）。实测 ecomm：

| 指标 | 值 |
|---|---|
| 实体数 | 135 |
| 字段数 | 686 |
| 摘要字符数 | **≈14,432** |
| 估算 token | **≈8k–11k**（中英混合） |

这批 token **每一轮都在**（多轮循环里 system prompt 不变，成本恒定）。它同时是注意力干扰源：
大部分问题只涉及 2–3 张表，模型却要在 135 张表的字段列表里做工具选择 —— 选择变慢、变错，
还会诱发「先翻几页数据看看有什么」这类探索性浪费调用。

### R5（摩擦）MCP 模式发现链路固定多一跳

MCP 按需发现（T23/T24）的范式是 `search_entity_tools` → `call_entity_tool` 两跳。
每个新实体查询固定多 1 轮。发现本身是对的（避免把 135 个动态工具全量塞进 tools/list），
但候选目录没有「按问题预筛」的机制，模型经常先搜、再猜、再调。

### R6（失控）推理与循环无护栏，失败呈现为误导性报错

- **reasoning 无循环检测、无长度上限**（`DefaultAgentService:305` 直接透传）；
- **输出预算默认 4096**（`iris.llm.max-tokens`），推理模型下 reasoning + 正文共享，偏小；
- `finish_reason=length` 被客户端直接抛异常（`OpenAiCompatibleAgentClient:225-228`），
  在 Agent 层被包装成 `error: 工具执行链路异常: LLM 输出被 max_tokens 截断…`（`DefaultAgentService:196-199`）——
  用户看到「链路异常」，实际是「预算耗尽 / 问题超出工具能力」；
- 轮数用尽的文案「模型仍在请求工具，终止循环」（`DefaultAgentService:190-193`）在 **0 次工具调用**时同样出现，属于误导。

### R7（策略）系统提示词没有「不可解问题」的合法出口

规则 1 严禁编造（对），规则 10 要求无数据时如实回答（对），但**没有一条**覆盖
「这个问题需要的查询能力当前工具不支持」—— 于是模型被规则 1 逼着硬扛，走向穷举。

## 3. 改进方案

### 3.1 MCP 工具设计（治本层）

#### A1 新增聚合工具 `aggregate_entity`（核心，强烈建议）

- **接口形态**：`aggregate_entity(entity, groupBy[], metrics[{op: count|sum|avg|min|max, field}], filters, having?, sortBy, limit, tenant)`。
- **底层**：Redis Query Engine 原生 `FT.AGGREGATE ... GROUPBY @field REDUCE COUNT 0 SORTBY ... LIMIT`。
  **可行性已实测**：`iris:ecomm:index:pay_payment` 的 `channel_id` 为 `NUMERIC + SORTABLE`，
  `FT.INFO` 确认可分组；聚合在服务端完成，不占模型 token。
- **收益**：「每渠道支付笔数 + TopN」从「≥6 轮且失败」压缩到 **2 轮**（1 次聚合 + 1 次作答）。
  统计、分布、TopN、按天/按状态分组全部覆盖。
- **缺点 / 边界**：只能聚合**索引字段**（未索引列不行，schema 里 `indexed/index` 元数据现成可用来预判并拒绝）；
  语法细节多（别名、SORTBY、DIALECT），需要像 T25/T31 那样配验收脚本（探针命名空间 + commandstats 标准）；
  跨表聚合仍需两步（先查维表拿 id，再过滤）——由 A3 补。
- **适用场景**：统计、排名、分布、按时间/状态分组。这是失败案例的**直接解**。

#### A2 维表展开（预关联）参数 `expand`

- **接口形态**：在查询工具上加 `expand: {channel_id: "pay_channel.channel_code"}`，服务端做 N+1 取值并回填合并行。
- **收益**：维表翻译类（id→名称/编码）跨表需求从 3–4 轮降到 1 轮；模型直接拿到可读结果，不再自己维护映射。
- **缺点**：服务端 join 实现复杂；任意深度展开有性能与授权风险；必须限制展开深度与目标表
  （沿用 T11 的授权∩字段约束，fail-closed）。
- **适用**：高频「按名称分组/展示」类。**建议放在 A1 之后做**，先解决统计，再解决可读性。

#### A3 `filters` 支持 IN 列表

- **接口形态**：`filters` 值支持数组（`{"channel_id": [1,2,3]}`），底层展开为逐值查或 TAG/NUMERIC 集合查询。
- **收益**：跨表聚合的第二步（拿维表 id 后一次取回全部目标行）1 轮搞定；也是 A1 跨表化的前置。
- **缺点**：IN 列表过长时退化为多次查询，需要上限（如 100）。
- **适用**：通用，实现小。

#### A4（可选，慎做）受控只读查询 DSL / SQL

- **形态**：一个固定工具，接受**受约束的查询 DSL 或只读 SQL**（白名单表/字段、只读、行数上限、超时、拒绝子查询写法）。
- **何时需要**：只有当分析需求长尾到无法用 A1–A3 枚举时（真正的自由探查场景）。
- **缺点**：白名单与执行计划的工程量大；对「平台不回查主库」的 T2 立项原则有张力（Redis 侧查询可做，
  回源 MySQL 则违背设计初衷）。**默认不做**，A1 覆盖 80% 场景后再评估。

### 3.2 调用策略（提示词与护栏层，见效最快）

#### B1 系统提示词补「能力边界」规则（P0）

新增一条规则，与规则 10（如实回答无数据）同级别：

> 需要分组统计/求和/排名而可用工具不支持时，**直接说明当前工具无法完成该聚合，并给出你能回答的替代标准**
> （如总量、按单渠道查询的方法），**严禁通过逐页拉取全量数据自行累计**。单次问题分页拉取不得超过 3 页。

- **优点**：改字符串立即生效，直接掐断复读与预算烧光的**主要诱因**；顺带把「穷举」这条路封掉。
- **缺点**：靠模型自觉，长尾仍会漏；必须配合 A1 落地后改写成「优先用 aggregate_entity」。
- **适用**：所有模型，立刻可上。

#### B2 工具元数据增强（P0）

`EntityToolFactory` 的参数 description 现在只说「上限 200」。补齐关键引导：

- `fields`：「**尽量只取需要的列**，可显著减小结果体积」（针对 R3）；
- 工具 description：写明「结果含 total 与分页信息」「**无聚合能力**，统计类问题请直接说明无法回答」；
- schema 摘要（若保留全量）里给每张表补一句**用途描述**（现在 yml 里部分表没有 description），
  让模型「先选对表再查」而不是「先查了再看」。

- **优点**：一次改动所有模型受益，与模型无关。
- **缺点**：描述变长会占 token —— 与 C1 的减载目标要一起权衡。

#### B3 循环护栏与失败呈现（P0）

- **同参重复检测**：同一工具 + 相同参数（或仅 page 递增的大分页循环）连续 ≥2 次 → 中断，注入
  「该路径已证明不可行，请改变策略或如实说明无法回答」；
- **reasoning 复读检测**：滑动窗口内重复片段超过阈值 → 截断 reasoning 并注入一句「请立即给出工具调用或结论」
  （不流式展示的部分不进上下文，检测发生在服务端拼接处，成本可忽略）；
- **轮数用尽时给「总结机会」**：最后一轮不再传工具目录，改为强制要求模型基于已获得的信息给出部分结论
  —— 把「报错」变成「有依据的部分回答」；
- **错误信息改写**：`finish_reason=length` → 「输出预算耗尽（不是链路故障）；该问题可能超出当前工具能力，
  建议简化问题、减小结果体积，或调大 iris.llm.max-tokens」；轮数用尽且 toolCalls=0 时，
  文案改为「模型未能发起任何有效工具调用（通常是输出预算被思考耗尽）」。

- **优点**：把最坏的失败模式（死循环 + 误导报错）变成可解释、可部分交付。
- **缺点**：护栏参数需要调（阈值太紧会误伤合法重试，规则 5 允许 1–2 次修正）。

#### B4 发现链路减一跳（P1，条件收益）

- 形态一：`call_entity_tool` 支持一次批量调用多个（name + args 数组）；
- 形态二：MCP 模式下把「上轮 search 结果的候选目录」保留在上下文，避免重复 search。
- **优点**：MCP 模式每问题省 1 轮；**缺点**：与 C1 减载有张力；**适用**：确认发现跳数占比高之后再做
  （先用 done 帧里的 `toolCalls` 统计验证）。

### 3.3 上下文管理（供给层）

#### C1 Schema 摘要分级注入（P1，收益明确）

现状 14.4k 字符（≈8k–11k token）常驻。改两级：

- **一级摘要（常驻）**：只注入「表名 + 一句话用途 + 关键关联」，135 行 ≈ 3–4k 字符；
- **二级详情（按需）**：字段级详情由 `get_schema(entity)` 现取（工具已存在，规则 2 的「别调 get_schema」要相应放宽），
  或按问题关键词先做一次轻量匹配、只注入命中表的全字段。

- **优点**：省 7k–10k token/轮；模型先选表再查，工具选择准确率上升，轮次自然下降。
- **缺点**：表需要**用途描述元数据**（当前 yml 只有部分字段有 description，表级描述要补 —— 一次性离线工作，
  **正好可以让 AI 来做**，见 §4）；多一跳 `get_schema`。
- **适用**：实体数多的 namespace（ecomm 135 表是重灾区）；实体少的 namespace 可保留全量（做个阈值切换）。

#### C2 工具结果硬裁剪（P1）

- 行数上限（建议 50 行/页，服务端在工具层裁，不动 `PageRequest.MAX_PAGE_SIZE`）+ 字节上限（如 32KB）；
- 超限时在结果里明确提示：「已截断，共 N 行；请用 filters 收窄 / fields 减列 / total 看全量」；
- 默认剥离大文本字段（备注、日志正文类），模型要时显式点名。

- **优点**：一行护栏防 context 爆炸，A1 未上线前就能显著降低复读概率。
- **缺点**：截断可能切掉模型需要的信息 —— 必须与「用 fields/total 精准取数」的引导（B2）成对出现。

#### C3 历史注入降载（P2）

现状 6 条 × 1200 字符 ≈ 最多 7.2k 字符。改为「用户问题原文 + 助手答案首行（≤200 字符）」，
或条数降到 3。**适用**：多轮追问场景对上下文连续性有要求的才保留；单问独立的演示场景收益明显。

#### C4 输出预算与默认值（P0）

- `iris.llm.max-tokens` 默认 4096 → **8192**（推理模型的 reasoning + 正文共享预算，4096 实测不够；
  成本上升约 1×，但换来「能说完话」）；
- 演示页 ⚙ 配置的输出预算默认值同步上调（上限 32768 已存在，不必动）。

### 3.4 交互澄清层（2026-09-11 增补）

#### D1 交互式问答澄清机制

- **机制（四步循环）**：
  1. **预判**：用户提问后、发起首个工具调用前，先对「需求意图 + 需要调度哪些工具、用什么标准」做一次内部分析
     （复用首轮 reasoning 完成，不增加独立 LLM 调用）；
  2. **澄清触发**：检测到用户语义或描述不清晰、存在歧义或关键信息缺失时（如时间范围未指明、「销售额」指下单
     金额还是支付金额、按天还是按月分组未定），**不强行查询**，主动发起澄清提问；
  3. **选项化**：澄清问题必须附带若干预设选项（2–4 个，来自 Schema 摘要与工具面的**真实可选标准**，
     禁止开放式空问），并**固定追加一个「其他」选项**，支持用户自行填写补充描述；
  4. **续跑**：用户完成选择或填写后，澄清结论带入会话上下文，**按原流程继续执行后续步骤**——
     不中断循环、不重复确认已明确的内容、澄清轮次不计入轮数预算。
- **落地分两档**：
  - **轻量档（纯提示词，可随 P0 当天先行）**：`SYSTEM_PROMPT` 新增一条规则——「问题存在歧义或关键标准缺失时，
    先输出澄清问题与编号选项（固定含『其他，请补充说明』一项），待用户答复后再调用工具；选项必须来自
    真实存在的字段/标准」。演示页零改动：澄清以普通答案呈现，用户回复天然进入下一轮上下文，
    「带入上下文继续执行」由现有多轮机制直接满足。
  - **完整档（协议 + 前端）**：SSE 新增 `clarify` 事件（结构化 `options[]` + `allowFreeText` 标记），
    前端渲染点选卡片与「其他」输入框；用户提交后经独立入口重新入队，服务端把选择以结构化形式注入
    会话上下文并继续原循环。改动点：`AgentEventSink` 事件协议、`AgentController` 恢复入口、
    `console/src/pages/AgentDemo.tsx` 渲染。
- **优点**：把「模型猜错标准 → 查完才发现 → 推倒重来」的浪费**前置到查询发生之前**，与 B1（能力边界）、
  E1（失败信号）互补——歧义澄清治「问得不清」，能力边界治「答不了」，失败信号治「事后才发现」；
  选项来自 Schema 真实字段，顺带完成一次轻量的标准教学（用户下次会自己说对）。
- **缺点**：完整档要动 SSE 协议与前端，跨端改动量最大的一条；澄清频率必须强约束——规则要限定
  「**仅关键标准缺失时**才澄清」，否则模型会把澄清当万能挡箭牌，交互轮次反而上升
  （护栏：同一问题澄清不超过 1 次，澄清轮不计入 max-iterations）；轻量档依赖模型自觉，选项质量不稳定。
- **适用**：时间范围/统计标准/分组维度缺失的高频歧义场景；与 C1 一级摘要配合时，选项生成基于常驻摘要
  即可完成，无需额外取数。

## 4. 专项研判：是否需要「AI 介入动态生成 MCP 工具」

**结论：不需要「运行时由 AI 现场生成工具」。需要的是「固定正交原语 + 离线 AI 研判 + 运行时生成查询参数」。
让 AI 在请求路径上动态发明工具本体，是拿确定性换灵活性，对这个项目是负收益。**

事实依据：

1. **缺口是原语，不是工具数量。** 失败案例缺的是 `GROUPBY COUNT` 一个原语加结果裁剪。
   A1–A3 三个参数化原语覆盖统计/TopN/分布/维表翻译/跨表取数 —— 集合有限、可枚举、**可回归测试**。
   用代码写死的确定性工具，失败时可定位到行（T25/T28/T31 都是这么定位的）；AI 生成的工具每次都可能不同，
   出错时分不清是「原语错了」还是「生成错了」。
2. **安全模型会被击穿。** T11 的授权是 fail-closed（授权∩字段约束、tags 鉴权层注入），前提是**工具面静态可审计**。
   动态生成工具 = 每次调用面都在变，白名单、授权、审计全部失效。对数据平台这是不可接受的风险面。
3. **工具面越大，模型选择越差 —— 本项目已实证。** 14.4k 字符的 schema 摘要已经让模型迷路；
   「支持任何需求场景」的工具集意味着工具爆炸，与精简目标背道而驰。MCP 官方工具设计指南同样是
   「少量正交工具 + 精确描述」的取向。
4. **AI 已经在正确的位置上了。** tool-calling 的本质就是「AI 现场生成查询参数（DSL）」——
   参数是可审计的字符串，工具本体是固定的可执行代码。缺的是 A1–A3 这几个原语，不是生成器。
   把「AI 生成参数」升级成「AI 生成工具」，只增加了不可预测性，没增加表达力。
5. **「任何需求场景」的真解是受控查询 DSL / 只读 SQL（A4）**：AI 生成查询语句（可白名单校验、可审计），
   执行器固定。即使走到这一步，生成的仍是**查询**，不是**工具**。
6. **AI 研判的正确位置是离线。** 用 AI 分析真实问题分布（统计类占多少、维表翻译占多少、跨表关联占多少）→
   决定补哪些原语、给哪些表建预置统计视图 → **人审** → 固化到代码/YAML。AI 当产品经理，工程师当实现者。
   表级用途描述（C1 需要）也适合离线用 AI 一次性批量生成、人审入库。
7. **唯一站得住的「运行时动态」形态**是「AI 从预定义算子库组合查询计划」（plan generation）——
   但那正是现有 tool-calling 循环 + A1–A3 原语就能达到的效果，不需要额外基建。

## 7. 自进化循环（2026-09-11 增补）

> 背景：老板指出系统缺「自进化路径」——用户提问答不上来或答得不理想时，应进入**异步、由管理员审查**的
> 自进化环节。本节给出完整链路设计。先划边界，再讲机制。

### 7.1 边界：进化的是「资产」，不是「运行时行为」

一句话：**AI 起草 → 管理员审查 → 版本化生效 → 回归门验证 → 可回滚**。五件套缺一不可。

允许被进化改变的**资产**（按改动成本/风险从低到高）：

| 资产 | 载体 | 生效方式 | 风险 |
|---|---|---|---|
| 术语/同义词表（业务黑话→字段/实体） | Redis Hash + 版本号 | 即时，注入 prompt | 低 |
| Schema 表/字段用途描述 | `deploy/schema/*.yml` | 热载（已有 schema hot-reload） | 低 |
| 成功查询范例库（问题→查询计划 few-shot） | Redis + 向量索引 | 即时，按需检索注入 | 低-中 |
| 提示词规则（SYSTEM_PROMPT 规则集） | 版本化文件 | 重启/管理端 reload | 中 |
| 预置统计视图/命名聚合 | YAML/代码 | 部署 | 中 |
| **新原语/工具**（如 `aggregate_entity`） | **代码** | **正常开发流程，不自动化** | 高 |

**不允许**的进化方式（与 §4 研判一致）：运行时 AI 自改提示词/自增工具/自改授权面；
无回归门的自动应用；把失败案例直接当 few-shot 塞回 prompt（未经人审的失败样本会教坏模型）。

### 7.2 信号层：答不好是可观测的，先别问用户

服务端在 `done/error` 收尾处已经有全部原始信号（`DefaultAgentService` 收尾逻辑 + SSE 帧流），
**零 LLM 成本**即可算出失败分类：

| 信号 | 判定 | 对应根因 |
|---|---|---|
| `finish_reason=length`（现抛异常） | 预算耗尽 | R3/R4 上下文爆炸、R1 穷举 |
| 轮数用尽且 `toolCalls=0` | 思考烧光预算，未行动 | R6/R7 |
| 同参重复调用触发护栏（P0 后有） | 穷举/循环 | R1 |
| 轮数用尽且仍有工具调用 | 复杂度超出能力 | R1/R2 |
| 答案含「无法/不支持/抱歉」 | 能力边界（弱信号） | R1/R7 |
| `cacheResult=miss` + 高延迟 | 无积累价值路径 | 优化机会 |
| 首轮工具选错实体后换表 ≥2 次 | 选表不准 | R4 |

显式反馈作为补充而非唯一来源：演示页 assistant 消息下加 👍/👎 + 一句话备注
（`POST /api/v1/agent/feedback`，关联 sessionId）。用户乱点会有噪声，故**隐式信号定类、显式信号定优先级**。

**落库纪律（T25/T31 教训直接适用）**：请求路径上只做 `XADD iris:{ns}:agent:evolution`（O(1)），
**严禁**在收尾路径 SCAN/KEYS；stream 用 `MAXLEN` 封顶（如 1 万条）防无限增长；
**只存查询计划不存数据行**（entity/filters/fields/轮次/失败类），数据行既涉及敏感信息又没有研判价值。
分类用规则引擎（确定、便宜、可解释），LLM 只在离线研判阶段用。

### 7.3 研判层：AI 的正确位置（离线起草）

`POST /api/v1/agent/evolution/triage`（管理员触发）或低频定时任务，对未处理失败做：

1. **聚类**：按 `失败类 + 涉及实体` 分桶，桶内用问题向量近邻（复用现有 OnnxEmbedder + HNSW 索引）再分组；
2. **起草**：每簇产出**拟议 artifact 草案**——术语表条目、schema 描述补丁、few-shot 范例、
   提示词规则草案，或「原语缺口」工单（如本次的 aggregate_entity，就是从一个失败聚类里长出来的）；
3. **只起草不生效**：草案进待审队列，带证据（原始问题、轨迹摘要、同类条数）。

LLM 调用发生在批处理里，成本可控；草稿质量要求「可直接采纳或小改」，不允许「建议人工进一步分析」这类空话。

### 7.4 审查层：管理员工作台（控制台第 14 页）

- 待审聚类列表：失败类、样本数、涉及实体、AI 草案 diff、证据展开；
- 操作：批准 / 编辑后批准 / 驳回（驳回理由回写，供下一轮研判校准）；
- 权限走 agent-keys 的 operator 体系；**匿名不可见**。

### 7.5 生效层与回归门

- **版本化是硬要求**：本项目**不是 git 仓库**，schema YAML 与提示词的每次变更必须在 Redis 里存
  `artifact 版本 + 上一版快照`，支持一键回滚——否则一次坏草案无法撤销；
- **回归门**：应用任何资产前，重放 §5 的基准问题集（含「不可解问题应如实说明」这类负样本），
  通过才生效，结果记入版本记录。进化没有回归门 = 引入不可控回归；
- 生效路径复用现有设施：schema YAML → 热载；术语/范例 → Redis 版本键。

### 7.6 运行时受益路径（进化库怎么反过来降轮次）

- **相似范例检索**：新问题进来 → embed → 在「成功轨迹计划库」KNN top-1~2 → 注入
  「类似问题曾用此查询计划」，模型跳过探索直接行动。复用现有向量基础设施，**这是降轮次最直接的进化产物**；
- **术语表注入**：按问题命中关键词注入相关条目（不是全量塞）；
- schema 描述补丁生效后，一级摘要（C1）的选表准确率直接受益。

### 7.7 落地顺序（挂在 §5 路线之后）

| 级别 | 内容 | 依赖 |
|---|---|---|
| **E1**（1 天） | 信号采集 + 失败案例库（XADD/分类/MAXLEN）+ 演示页 👍👎 | **P0 先落**（否则信号全是 length 截断，分类失真） |
| **E2**（2–3 天） | 进化工作台 MVP（聚类列表 + AI 草案 + 批准/回滚 + 基准重放门） | E1 |
| **E3**（2 天） | 相似范例检索注入 + 术语表注入 | E2 + P1 的 C1（一级摘要腾出的上下文空间正好装范例） |

一句话总结：**自进化 = 把 §2 的七个根因从「一次性人肉发现」变成「信号自动捕获 → AI 离线起草 → 人审 →
回归门 → 版本化生效」。它不改变 §4 的结论——进化的是资产，运行时行为永远由固定的原语和经人审的资产决定。**
