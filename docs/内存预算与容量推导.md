# 内存预算与容量推导

> 2026-09-13 首版。背景：16G Mac 开发机跑 11.67G Docker VM，Redis 稳态 4.95G RSS，
> 出现「冷查询 2s+ / 热查询 0.15s」的 14 倍波动与 AOF 13.9GB 积压。
> 本文把当天的实证数据沉淀为**可推导的容量账本**，供后续扩容/缩容/换机时复算。
>
> **口径注记（2026-09-21）**：本文账本以**完整 ecomm 数据集**（135 表 367 万行）为口径。
> 仓库内置的抽样版（`deploy/mysql/init/sample-data/iris_demo_sample.sql`，约 11.8 万行 ≈ 全量 3.2%）
> 对应 Redis 占用约为全量的 1/30（≈0.2 GB 量级），新用户用抽样数据不会触发本文的换页/OOM 场景。

## 1. 机理：为什么冷查询会慢

```
16G 物理内存（Mac mini / MacBook M1）
 ├── Docker VM 配额 11.67G（硬上限，曾 OOMKilled）
 │    ├── iris-redis      稳态 RSS ≈ 5G（dataset 4.24G × 碎片 1.21）
 │    ├── iris-debezium   ≈ 0.5G
 │    └── iris-mysql      ≈ 0.4G
 ├── macOS + IDEA + 浏览器 ≈ 5~7G
 └── 缺口 → macOS 把 VM 的冷页换出到磁盘 swap（实测 swap used 10.9G/12.3G）
```

Redis 冷数据页被换出后，冷查询 = 从磁盘 swap 读回 → 秒级；热查询 = 物理内存 → 毫秒级。
**实证**（同一条 GROUPBY @channel_id 聚合，5 万行 × 2957 组）：

| 状态 | 耗时 |
|---|---|
| 冷（首跑，swap 页入） | 2.13s |
| 温 | 0.78s |
| 热 | 0.15s |

连 3000 文档小索引（pay_channel）的 FT.SEARCH LIMIT 50 都曾跑出 1.7s——
**慢的不是聚合算力，是整机换页**。索引本身无罪：channel_id 已是 SORTABLE，GROUPBY 直读索引。

## 2. 内存账本（2026-09-13 实测）

| 项 | 值 | 推导/依据 |
|---|---|---|
| dataset.bytes | 4.24 GB | MEMORY STATS；320 万键 × 平均 1322B |
| ├ JSON 文档镜像 | ≈3.3 GB | 135 表 3.67M 行全镜像，本体无水分 |
| ├ CDC stream 保留窗 | 0.87→0.09 GB | 125 流 122 万条顶满旧 maxlen 10000（每条含全量行 JSON，均值 711B/条）；maxlen 降至 1000 后 ≈87MB |
| └ 索引 + 开销 | ≈0.8 GB | 倒排 8.9MB/实体 + HASH/SET 索引 + hashtable 136MB |
| used_memory（allocator） | 4.08 GB | INFO memory |
| RSS = dataset × 碎片系数 | 4.95 GB | 碎片 1.21（allocator-fragmentation 1.21，健康） |
| **峰值 = 稳态 + fork COW** | **8.84 GB（peak.allocated 实测）** | BGSAVE/BGREWRITEAOF 的 copy-on-write 上界 ≈ 数据集大小 |
| AOF 磁盘 | 基线 1.0~1.5 GB | BGREWRITEAOF 后实测 1.01GB；增量速率 ≈1.4GB/天（44M 变更/3 天） |

**核心公式**：

```
VM 配额 ≥ 峰值内存 = 稳态 RSS + max(BGSAVE COW, BGREWRITEAOF COW) ≈ RSS × 1.8
```

本机：4.95 × 1.8 ≈ 8.9G < 11.67G 配额 ✓（配额不缩——缩到 10G 会让 rewrite 峰值顶格）。

## 3. 操作红线（全部有事故案底）

1. **全量导入前**：`CONFIG SET auto-aof-rewrite-percentage 0`（导入期高写入下 rewrite COW 会 OOM，T26 实证 OOMKilled 137）。
   **导入后 RSS ≤ 5G 时必须改回 100**——2026-09-13 忘改回，3 天积压 AOF 13.9GB。
2. **RDB 关闭**（`--save ""`）：持久化由 AOF(everysec) 承担，RDB 是最频繁的 fork 源（T26）。
3. **容器重启后**：`FT.CONFIG SET TIMEOUT 2000` 需重设（模块参数不进命令行）。
4. **AOF 手动收缩**：低峰执行 `BGREWRITEAOF`，期间盯 RSS（fork 后 COW 随写入爬升）。
5. **清 swap 唯一手段 = 重启 Docker Desktop**（10.9G swap 全清，冷查询立即恢复毫秒级）；
   必须在 BGREWRITEAOF 完成后做（中途重启杀 fork 白干）。

## 4. 治理手段与效果（2026-09-13 落地）

| 手段 | 层 | 效果 |
|---|---|---|
| `stream-maxlen: 10000 → 1000` | 配置 | RSS -780MB（-15%） |
| BGREWRITEAOF + percentage=100 | 运维 | AOF 13.9GB → 1.01GB；防再积压 |
| 客户端 `iris.redis.timeout-ms: 2000 → 8000` | 配置 | 冷查询不再被客户端抢先掐死；查询护栏仍在服务端 FT.TIMEOUT |

> 注：P1 曾同时落地预聚合 `iris.preagg.*`（计数 HASH 直读）与索引预热 `iris.warmup.*`（定时分组聚合焐热索引页），2026-09-14 老板评审后以「收益面窄（只覆盖显式声明维度）+ 演示语义渗进配置/日志」为由整体移除，见总览 §5.6。

**残余风险**：数据镜像 3.3G 是本体，16G Mac 上 swap 压力只会缓解不会归零
（冷查询尖刺靠客户端 timeout 8000 + 服务端 FT.TIMEOUT 兜底；生产部署不在宿主机换页环境，此问题不成立）。
根治选项（未立项，P2 已否决）：演示数据集缩表、镜像 TTL/LRU 化。

## 5. 推导速查（换机/扩容时重算）

```
稳态 RSS   ≈ 行数 × 每行 JSON 大小 × (1 + 镜像开销 10%) × 碎片 1.21
             （本机：3.2M × 1322B × 1.21 ≈ 5.1G ≈ 实测 4.95G）
stream 窗  ≈ 流数 × stream-maxlen × 711B/条（全量行 JSON 均值）
AOF 磁盘   ≈ base 1.2G + 变更速率 × 重写周期（percentage=100 → 增量达 base 即重写）
VM 配额    ≈ 稳态 RSS × 1.8（fork COW 余量）
客户端超时 ≳ 服务端 FT.TIMEOUT + 冷页余量（本机 8000/2000）
```
