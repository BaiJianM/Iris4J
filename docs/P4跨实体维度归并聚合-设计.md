# P4 维度归并聚合（语义层原语）——通用设计 v2（2026-09-11）

> v1 设计（同日稍早）围着 ecomm 支付渠道案例特化，已废弃重写。
> 定位约束：**iris-lite 是开源的中间件级产品，演示库只是验收载体，接入方数据来自各行各业。**
> 本设计的一切机制不得包含任何行业语义；案例只能出现在示例、配方、测试中。

## 一、通用问题定义

OLTP 库的投影（CDC 忠实行投影）天然是「窄表 + 外键」形态——**业务分析永远需要按关联实体的维度分组统计**，这是跨行业的普遍形态：

| 行业 | 事实表 | 维度路径 | 典型问题 |
|---|---|---|---|
| 电商 | 支付流水 | channel_id → 渠道表.channel_type | 各支付方式多少笔 |
| SaaS | API 调用日志 | endpoint_id → 服务表.service_tier | 各套餐调用量 |
| 物流 | 运单 | warehouse_id → 仓库表.region | 各区域发货量 |
| 制造 | 质检记录 | production_line_id → 产线表.factory_zone | 各厂区不良率 |

共同结构：**事实表的 FK 字段 →（关系图已有的 relatedEntity 边）→ 维表上的低基数维度字段**。FT.AGGREGATE 不跨索引 join，维表全量拉取又超分页限制——这不是支付渠道的问题，是「投影 = 源表行」这一架构决策的必然推论：**投影保行级忠实，归并必须在查询侧补**。

## 二、核心抽象：维度路径（dimension path）

**不做 `translate` 三字段参数**（那是给单个案例开的小门），而是把归并做成 group_by 的一等语法——**维度路径**：

```json
{
  "entity": "pay_payment",
  "group_by": ["channel_id->pay_channel.channel_type"],
  "metrics": [{"op": "count"}],
  "sort_by": "count", "sort_desc": true, "limit": 10
}
```

- 语法：`<fk字段>-><维表实体>.<维度字段>`，单条 group_by 项一个路径
- **解析依据是 schema yml 里接入方声明的 `relatedEntity`**（T15 关系图谱）——图谱在 G1 就已建立，这是它的第一个查询侧消费者：**图谱不只注入 prompt，还驱动查询重写**
- 对模型零新增概念：它已经知道 relatedEntity（schema 摘要里 `→` 标注），路径只是把它写出来
- 接入方只要声明过关系（本来就该声明），任意行业的维度归并**自动可用，零额外接入成本**

### 解析与校验（fail-closed，报错即文档）

1. 路径拆解 → fk 字段须存在于事实表 schema 且 `relatedEntity` 非空
2. `relatedEntity` 必须与路径中维表实体**精确一致**（防乱 join；一跳 v1，多跳 BFS 留 v2）
3. 维度字段须存在于维表 schema（是否须已索引：v1 不强制——归并读的是投影文档非索引；未来优化再收紧）
4. 报错文案附带合法写法示例（P1 同款原则：报错即文档，不让模型猜）

## 三、维度解析器（DimensionResolver）——策略分层的独立组件

映射拉取是独立端口（application 层接口，infrastructure 实现），**策略按维表规模自适应**，不假设演示库量级：

| 策略 | 适用规模 | 机制 | 版本 |
|---|---|---|---|
| R1 逐键 pipeline | ≤ 维表阈值（默认 2 万行，配置化） | pipeline 批量 JSON.GET（只取维度字段 path，批大小可配默认 500）+ 应用内 TTL 缓存 | v1 |
| R2 派生维度索引 | 大维表（10 万+） | CDC 对**声明的维度字段**维护 `iris:{ns}:dimidx:{entity}:{fk}->{dim}` HASH（fk 值 → dim 值），归并时一次 HGETALL | v2 |
| R3 维表 FT 批查 | 中维表折中 | 维表自身 FT.SEARCH 按主键 IN 分批 | 备选 |

- **策略切换依据**：维表投影规模（索引 num_docs，一次 FT.INFO 即得），阈值配置化——不是拍脑袋魔法数，是可按接入方硬件调整的预算参数
- **缓存一致性不靠 TTL 猜**：归并结果的缓存/围栏失效走 **T19 版本围栏**——维表（via 实体）加入 touched 集合，维表数据一变，依赖它的归并结果自动失效。应用内 TTL 缓存只是省重复拉取的性能优化，正确性由围栏保证（TTL 设长也不出错）
- **模块边界**：Resolver 的 R2 在 cdc 消费侧只追加「读已声明维度配置 + 写 HASH」，不触碰「cdc 只消费不查询源库」红线

## 四、归并语义（merge 代数，分布式聚合标准）

| op | 归并规则 | 性质 |
|---|---|---|
| count | 相加 | 结合律 |
| sum | 相加 | 结合律 |
| avg | 保存 (sum, count) 对，归并后 sum/count | 可合并平均 |
| min / max | 取极值 | 幂等+结合 |

实现按 (sum, count) 对保存中间态，最终行才物化——这是标准 partial aggregation 语义，为未来「分组下推/分片并行」留同一接口。

## 五、配置项（全部可配，默认值给出推导依据）

| 配置 | 默认 | 推导 |
|---|---|---|
| `iris.aggregate.dimension.max-input-groups` | 20000 | 归并前组数上限；每组中间态 ~200B → 峰值 4MB 堆内，任何生产 JVM 安全；超限拒绝并建议加 filters |
| `iris.aggregate.dimension.fetch-batch` | 500 | pipeline 批大小，网络往返与内存的平衡 |
| `iris.aggregate.dimension.strategy-r1-max-rows` | 20000 | R1→R2 切换阈值（v1 只有 R1，超限直接拒绝并提示维度索引路线图） |
| `iris.aggregate.dimension.unknown-group` | `keep` | 映射缺失策略：keep（UNKNOWN 组）/ discard / error，接入方按业务选 |
| `iris.aggregate.dimension.cache-ttl-seconds` | 60 | 仅性能优化；正确性由 T19 围栏保证，故 TTL 可安全调大 |

## 六、响应契约

```json
{
  "entity": "pay_payment",
  "totalGroups": 8,          // 归并后组数（limit 作用于此）
  "inputGroups": 2957,       // 归并前组数，供调用方声明口径
  "dimension": "channel_id->pay_channel.channel_type",
  "rows": [{"channel_type": "WECHAT", "count": 12345}, ...]
}
```

## 七、治理链（全部复用，零新增概念）

- **租户 / T11**：归并只作用于聚合结果与维表文档读取；via 实体若多租户，同一套强制校验
- **T19 围栏**：touched 实体 = 事实实体 + 维表实体
- **RepeatGuard / ResultTrimmer**：作用于归并后输出
- **缓存装饰链**：归并查询与普通聚合同走 SemanticCachedEntityQueryService 链（缓存 key 天然含路径语法，不同维度不同 key）

## 八、明确不做（v1 边界）

- 多跳路径（`fk1->e1.f2->e2.dim`）：图谱 BFS 解析，v2——一跳覆盖绝大多数行业场景（上表 4 例全部一跳）
- 表达式维度（按时间 bucket、CASE WHEN 归类）：与归并正交，另立任务
- 写入侧 enrich / 预聚合统计表：破坏投影纯净性 / 口径管理成本（v1 已论证废弃，除非 R2 实测仍不够）

## 九、落地拆步

2. **DimensionResolver 端口 + R1 实现**（infrastructure，半天：pipeline 拉取 + merge 代数 + 配置项）
