# 查询路径规划策略——检查结论与设计（2026-09-11）

## 一、检查结论：**部分存在**。「关系图谱」已有，「AI 预生成」与「意图路径配方」没有

### 已存在的（可直接复用）

| 能力 | 位置 | 现状 |
|---|---|---|
| **关系图谱（可复用）** | `context/schema/FieldSchema.relatedEntity` + `EntitySchema.foreignKeyFields()` | 每个外键在 schema yml 声明 `relatedEntity: <目标实体>`，即构成 A→B 关系边；`EntitySchema` 紧凑构造器强制 FK 字段必须建索引 |
| **双向关系导航** | `application/RelatedEntityService`（T15，对标官方 Context Retriever Related Entity） | 正向（多对一：FK 值查目标行）+ 反向（一对多：枚举 namespace 全部指向本实体的 FK 声明）；**走完整治理链**（鉴权/缓存/索引下推自动生效），不是旁路 |
| **工具暴露** | `get_related_entities`（Agent 直连目录 + REST `RelatedEntityController` + MCP） | 提示词规则：「跨实体关联请先用本工具拿主键，再用 get_related_entities 导航」 |
| **关系人工编辑** | T20 控制台 Schema 页关系映射编辑（operator 专属） | 人工维护 FK 声明的 UI 入口 |

### 不存在的（本次设计补齐）

1. **接入时自动解析源库**：应用侧零处引用 `information_schema`（全仓 grep 实锤）——FK 关系 100% 人工在 yml 声明，无自动发现、无 AI 分析。
2. **典型查询意图 → 预置推荐路径**：无任何「意图 → 路径」映射存储；模型每次现场推理关联链。
3. **预置路径 → 最优工具组合**：无；代价是 MCP 模式下模型靠 search→call 反复试错（2026-09-11 实测「手机号查订单」走了 6 轮 6 工具，含一次静态兜底和一轮重复搜索）。

## 二、设计：G1 接入期图谱预生成 + G2 意图路径配方 + G3 运行时最优组合

### G1 接入时自动解析，形成可复用关系图谱（补「AI 预生成」缺口）

**新增 `application/SchemaBootstrapAnalyzer`**（只做分析建议，不静默改 Schema）：

1. **结构解析（确定性代码，不靠 LLM）**：接 `information_schema.KEY_COLUMN_USAGE / REFERENTIAL_CONSTRAINTS`，拉取全库表、列、主键、真实外键。
2. **FK 推断（无显式外键的库）**：命名约定 + 类型匹配推断候选边（`user_id` → `usr_member.id`、`order_id` → `ord_order.id`），输出带置信度（explicit / inferred-high / inferred-low）。
3. **AI 增强（一次批量 LLM 调用）**：把表清单 + 列类型 + FK 候选打包给 LLM，生成三样东西——①每实体一句话业务描述（**正好合并遗留项 C1 表级描述离线补齐**）；②每条 inferred 边的人工可读理由；③典型查询意图清单（见 G2）。
4. **产出物（人工审核后生效）**：`deploy/schema/graph/{namespace}.graph.yml`——只含增量元数据（relations 建议 + descriptions + recipes），**不覆盖**现有 schema yml；operator 在 T20 界面 diff 审核后合入。红线沿用：Schema 治理链、fail-closed、静默保留旧 Schema 的教训（reload 后必须显式对账生效）。

### G2 典型查询意图 → 预置推荐路径（配方 recipes）

`{namespace}.graph.yml` 中新增段：

```yaml
recipes:
  - intent: "查某用户的下单信息"
    match: ["手机号", "会员", "下单", "订单清单"]      # 意图匹配关键词
    anchor:                                            # 锚点：业务标识 → 实体主键
      param: user_key                                 # 手机号或会员 id
      resolve: usr_member                             # 先解析出 usr_member.id
      by: [mobile, id]                                # 支持的锚点字段
    path:                                             # 预置最优路径
      - step: usr_member WHERE mobile=? (或 id=?)     # 1 次索引查询
      - step: ord_order WHERE member_id=?             # 反向关系，1 次索引查询
    tools: ["query_entity", "get_related_entities"]   # 推荐工具组合
    hint: "计数直接读 ord_order 查询的 total，勿逐页拉取"
```

**注入方式（关键取舍：不新增工具，注入 system prompt）**：namespace 的 recipes 通常个位数~十几条，每条 2-3 行，直接注入 `SYSTEM_PROMPT`（与 schemaDigest 同段，参与指纹）——模型第 1 轮就知道完整路径，**省掉一次「调路径推荐工具」的往返**。规模超限时（>20 条）降级为 `recommend_query_path(intent)` 按需工具。

### G3 运行时最优工具组合（最少调用次数）

预置路径把「发现/推理」前置到了接入期，运行期只剩确定性执行：

| 场景 | 现状（实测） | 有 recipe 后 |
|---|---|---|
| 手机号查订单清单+计数（MCP 两跳模式） | 6 轮 6 工具（search→call→静态兜底→再 search→再 call） | **2 轮 2 工具**：`query_entity(usr_member,{mobile})` → `get_related_entities` 或 `query_entity(ord_order,{member_id})`（total 即单数） |
| 直连模式同类问题 | 3-4 轮 | 2 轮 |
| 语义缓存命中 | — | 0 次 LLM |

规则固化进提示词（并入规则 13）：**命中 recipe 时按 path 顺序执行，锚点字段优先用 resolve 实体；统计优先 aggregate_entity（G2 的 hint 提醒 total 即计数）**。执行仍全部走既有治理链（鉴权/缓存/版本守卫不变）。

### G4 存储与更新

| 数据 | 存储 | 更新机制 |
|---|---|---|
| 关系边 | schema yml 的 `relatedEntity`（现状不变） | T20 人工编辑 / G1 建议 diff 合入；Schema 热载 3 秒对账 + tools/list_changed 广播（现成机制） |
| 描述 + recipes | `deploy/schema/graph/{ns}.graph.yml` | 外部目录**同一热载机制**（一层平铺扫描已支持，新增 graph 子目录或平铺 `{ns}.graph.yml`）；内容 SHA-256 指纹并入 `/info` 的 promptDigest 暴露 |
| 源库 DDL 漂移 | — | G1 解析器支持离线重跑：对账 information_schema vs 现有图谱，漂移出报告（不自动改）；也可挂 Debezium DDL 事件触发 |
| 版本与审计 | graph yml 头部 `generatedAt / sourceFingerprint(表结构快照 hash) / reviewedBy` | 再生成永远是「新建议版本」，人工确认后替换——**AI 生成、人工批准、热载生效**三级 |

## 三、落地拆步（按收益排序）

1. **G2 最小版（半天）**：手写 ecomm 3-5 条高频 recipe（查订单/查会员/查商品库存）注入提示词——不动 Java，立竿见影压 MCP 两跳抖动。
2. **G1 解析器（1 天）**：information_schema 解析 + 推断 + 报告输出（先不出 LLM 建议），合并 C1 描述补齐。
3. **G1 AI 增强 + graph yml 热载（1 天）**：LLM 批量生成描述/recipes + 指纹暴露。
4. **漂移对账（半天）**：离线脚本或管理面端点。

> 以上四步已于 2026-09-11 当天全部落地，实测效果见 §1.1 与当日工作日志。

## 四、外部调研：业界更优方案对照（2026-09-11）

> 调研动因：老板指出 G1-G4 只是自有思路，要求网搜业界是否有更优解。以下为 6 轮检索的综合结论。

### 4.1 业界方案盘点

| 方案 | 代表 | 核心机制 | 与本项目的关系 |
|---|---|---|---|
| DDL/文档/问答对 RAG | Vanna.ai | 三类训练数据（DDL、业务文档、问题→SQL 对）入向量库；提问时检索 top-10 注入 prompt | G1 ≈ DDL 训练；**Q→配方对 = 自进化的现成范式** |
| 语义层 | Cube / dbt Semantic Layer / LookML | canonical 指标/维度/join 定义层，LLM 不写 SQL 只调语义 API；AtScale TPC-DS 准确率 20%→92.5% | 配方文件 `graph.yml` 本质是**轻量语义层**；完整产品化（指标定义/编译器）超出本项目边界 |
| Schema linking 检索 | AWS GenAI Atlas / ActiveWizards | embedding 检索相关表/列/样例查询，只注入相关子集而非全 schema | 当前 5 条配方全量注入可行；**配方增长后需升级为检索式 top-k 注入** |
| 意图路由 | 多家生产架构共识 | 前置分类（data_lookup / doc_search / schema_exploration / out_of_scope）再路由，避免所有输入都进 agent 循环 | 本项目缺口；现有「规则 11-13 + ask_clarification」覆盖了澄清与边界，但无显式前置分类器 |
| ReWOO / Plan-and-Execute | ReWOO 论文 / LangGraph | 先出计划 DAG、工具并行执行、单次合成，LLM 调用从 ~10 降到 2（成本差 3-4 倍） | **不适用为主**：数据查询步骤强依赖上一步观察（先拿 id 再查关联表），无法盲排 DAG；轮次已由配方+RepeatGuard 压到 4-5 轮 |
| 自进化 skill library | Voyager（arXiv:2305.16291） | 验证成功的程序+描述 embedding 入向量库，新任务检索 top-5 复用/组合；防灾难遗忘（存程序不存权重） | **E1-E3 的业界参照**：成功会话的工具序列整理为可复用配方候选 |
| golden dataset 反馈环 | Hacklines/ActiveWizards | 每次（问题, 正确查询）人工纠正对入库，做 few-shot 注入 | 自进化的**低成本近似**，比 Voyager 全自动更稳 |
| 查询验证层 | 通用生产模式 | parse / dry-run / EXPLAIN cost / deny-list / 行列级安全 / 审计 | 本项目已有等价物：字段校验 fail-closed（聚合/查询均走 schema 白名单）、T11 授权∩字段、RepeatGuard 防失控 |
| 语义缓存 | AWS MemoryDB + Bedrock | 语义缓存命中的参数化查询免重复推理 | 已有 T16 两级 LLM 缓存 + KNN 0.85 重排门槛，**无差距** |

### 4.2 结论：G1-G4 方向正确，业界无「推翻级」更优解；三个可吸收增量

1. **配方自进化循环（吸收 Voyager + Vanna Q-A 对 + golden dataset，对应原 E1-E3 的低成本重启路径）**：
   - 数据源现成——每次 agent 会话的工具调用序列已留痕；RepeatGuard/轮次数可判定会话是否「顺畅」。
   - 机制：会话结束后，把「高频顺畅会话的（意图→工具序列）」整理为 recipe 候选（yml 草稿），**人工审核后合入 graph.yml 热载**——与 G1 的 enhance 子命令同一条审核链，全自动 Voyager 模式明确不做（LLM 生成会编造工具名，已在 enhance 实测中实锤）。
   - 存储就地复用：仍是 `{ns}.graph.yml` 的 recipes 块，无新基础设施。
2. **检索式配方注入（配方 >10 条时的升级项，当前不急）**：recipesBlock 全量注入在配方少时最优（无检索开销、无漏检）；配方规模上来后改为 embedding 检索 top-k——LLM 缓存已有 `:vecidx` ZSET + 过期管理同款基础设施可复用。
3. **意图路由前置（低优先）**：业界前置分类器主要收益是给非数据类请求省 token/轮次；本项目规则 13（能力边界）+ ask_clarification（D1）已在 prompt 层覆盖同一职责，且显式分类器要加一次 LLM 调用。**暂不做**，等非数据类请求占比成为实测问题再议。

### 4.3 明确不采纳项（有据）

- **ReWOO/并行 DAG**：查询链存在硬依赖（实体 id → 关联表），盲排 DAG 会放大无效调用；论文场景（独立 fan-out 检索）不匹配。
- **直接 Text2SQL / 完整语义层产品**：本项目架构是「工具调用 + fail-closed 校验」而非生成 SQL，语义层的 verified-queries 思想已被 recipes 覆盖；引入 Cube/dbt 属重基础设施，违反单体 8 模块的体量约束。
- **自动 schema 文档全量生成**：G1 analyze 已输出表注释，C1 离线补齐即等价，不需要常驻服务。
