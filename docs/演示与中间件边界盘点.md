# 演示代码与中间件代码边界盘点（2026-09-13）

> 背景：agent 演示及前端页面不在本项目作为中间件的部署架构体系内，直接集成不对；
> 目标是把演示相关代码抽至独立模块。本文档是拆分前的边界盘点。
> **状态：已实施（形态 A，2026-09-13 当日落地）**——实施结果与第五节略有出入，
> 以「六、实施记录」为准。

## 一、判定标准

| 判定 | 含义 |
|---|---|
| **中间件** | 外部接入方（应用/Agent/运维）通过 REST/MCP 消费的能力：实体查询、缓存、记忆、CDC、Schema、安全治理、MCP 服务面 |
| **演示** | agent 聊天演示循环（SSE）+ 配方自进化闭环 + 前端 console——服务于「给人看」的验收载体，不是接入方契约 |

## 三、中间件正式能力（留在核心）

- **web/lifecycle/dto**：全局异常、健康、启停护栏、请求 DTO

### application 模块
- query（含装饰链）、cache、memory、cdc、ops 全部
- **`agent/AgentToolDispatcher.java`（含 ToolContext/DispatchResult）——重要澄清**：grep 实证 MCP 路径（DynamicToolExecutor/EntityQueryMcpTool）对它只有注释提及与未使用 import，真实执行直接走 EntityQueryService；**唯一真实使用方是 DefaultAgentService** → 它是演示循环专属，应随演示抽走（或迁入更中性的包名）

## 四、纠缠点（拆分时的决策点）

1. **AgentToolDispatcher 的包归属**：物理在 `application/agent`，但实为演示专属（见二）。抽走后 `application/agent` 包只剩 key 管理三件套——包名需重组（如 key 管理迁 `application/security` 或保留 agent 包但语义改为「agent 接入治理」）。
2. **演示模块与中间件的依赖向**：演示需要调用 EntityQueryService 链头、LlmCacheService、MemoryService、Dispatcher——依赖向应为 `demo → application`（+api 不行，api 是装配层）。若演示做成 Maven 模块：`demo` 依赖 `application`(+`infrastructure` 运行时)；若做成独立工程：走 REST/MCP 调中间件（更彻底解耦，演示即「第一个外部接入方」，最有说服力——但聊天循环里的 ToolContext 直连分发需要改为 MCP 调用，工作量更大）。
3. **Agent key 治理的归属**：`AgentKeyRegistry`（api/security）是中间件安全面（T11，外部 Agent 接入鉴权），**留核心**；`AgentKeyStore/Entry/AdminService` + `AgentKeyAdminController` 是它的管理端点——属于中间件运维面，留核心；演示页 AgentKeys.tsx 只是 UI 消费方，随 console 抽走。
4. **console 的 API 耦合**：console 调 `/api/v1/*` 全家桶（数据面+运维面+演示 SSE）。抽出去后要么 CORS/反代打通，要么演示工程独立部署——部署形态需拍板。
5. **配置段迁移**：`iris.llm.*`/`iris.agent.*` 随演示走；但 LlmClient（T5 记忆抽取、留痕摘要用）是中间件能力，其供应商配置与演示聊天配置可能共用同一组 key——拆分时要分清「中间件内嵌 LLM 能力」与「演示聊天」两份配置。
6. **verify 脚本与文档**：`deploy/verify/*` 中 agent 演示相关段（verify-agent-demo 等）随演示走；README/总览的演示章节标注为演示模块说明。

## 五、实施记录（2026-09-13，形态 A 已落地）

实际落地与第五节的差异：

1. **多拆了一个 `web` 模块**。原因：api 是 boot 模块，spring-boot repackage 后的
   fat jar（BOOT-INF 结构）不能再作为依赖被 demo 引用。解法 = 把 api 的 HTTP 面
   （controller/mcp/security/dto/web/config/lifecycle，包名不变）整体迁入
   `web`（普通 JAR）；api 只剩 `IrisLiteApplication` + application.yml + boot 插件，
   **产物名不变**（`api/target/iris-lite-api-0.1.0-SNAPSHOT.jar`，启动习惯零变化）。
2. **包名全部保持原样**（拆分包跨 jar 合法，零 import churn）：
   - `web`：`com.iris.lite.api.*`（原 api 包全套，除启动类）
   - `demo`：AgentController 原位入 `com.iris.lite.api.controller`；
     application/agent 7 类（AgentService/DefaultAgentService/AgentChatClient/
     AgentEventSink/AgentToolCatalog/AgentToolDispatcher/McpToolPort）+
     QueryPathAdvisor + RecipeDraftStore 原包入 demo；
     infrastructure 4 实现（OpenAiCompatibleAgentClient/StreamableHttpMcpClient/
     YamlQueryPathAdvisor/LettuceRecipeDraftStore）原包入 demo；
     console/ → `demo/console`
   - 留守 application/agent：AgentKeyAdminService/AgentKeyStore/AgentKeyEntry（中间件安全面）
3. **依赖修正**：demo 显式依赖 iris-lite-infrastructure（compile）——LettuceRecipeDraftStore
   等实现类引用 RedisAdapter，runtime 传递不满足编译期可见。
4. **指标**：心跳池 gauge 随演示迁 demo（`demo/config/DemoExecutorMetricsConfig`）；
   web 的 ExecutorMetricsConfig 保留记忆抽取/会话摘要两池。
5. **顺手修**：GlobalExceptionHandler 补 `NoResourceFoundException`→404（拆分后中间件
   jar 收到 /agent/* 请求不再以 500 假象报错）。
6. **配置**：demo 的 application.yml 为 api 全量拷贝（demo 进程 = 中间件全量 + 演示；
   注意开源前两个 yml 的明文 key 都要清）。
7. **构建/冒烟**：全量 BUILD SUCCESS；内容隔离验证（api jar 演示类 0 条目、demo jar 全量）；
   api jar :8080（/agent/info 404、数据端点 200）、demo jar :8080（/agent/info 200、
   数据端点 200、agent/info 正确读出 LLM 配置）双冒烟全过。

**启动方式**：
- 中间件：`java -jar api/target/iris-lite-api-0.1.0-SNAPSHOT.jar`（外部接入方，无演示端点）
- 演示：`java -jar demo/target/iris-lite-demo-0.1.0-SNAPSHOT.jar`（全家桶含 /api/v1/agent/* 与 console；
  console dev 模式 `cd demo/console && npm run dev`）
